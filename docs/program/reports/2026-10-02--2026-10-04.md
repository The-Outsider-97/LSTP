## Problems discovered / self-review

The previous `PacketEnvelope` implementation only rejected an empty version string. That meant values such as `1.0` or `latest` were accepted by the model even though v0.1 consumers are required to reject or explicitly route unsupported versions. Because no negotiation/router exists, accepting such values was too permissive.

The model also accepted arbitrary JSON values for `carrier`, `audit`, and `extensions`, despite their envelope role being object-shaped. In particular, a scalar extension value provided no enforceable namespace boundary. This was a reliability and future security risk because extension data could later be interpreted inconsistently by hosts.

The fix intentionally remains narrow: it does not create an extension registry or interpret extension payloads.
